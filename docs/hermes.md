## Path A: agent-directed MCP

Set `mcp_servers.earshot.url: https://YOUR-RELAY/mcp` and `mcp_servers.earshot.headers.Authorization: "Bearer ${EARSHOT_API_TOKEN}"` with the token in **that profile's** 0600 `.env`; use `hermes config set`, not an inline token in the YAML. `hermes mcp test earshot` resolved the placeholder, connected to HTTP `/mcp`, and listed `say`, `receipt`, `recent`, `status` (four tools). `say` advertises `readOnlyHint: false`, `destructiveHint: false`, `idempotentHint: false`, `openWorldHint: true`. `receipt` advertises `readOnlyHint: true`. With `trust: untrusted`, an unapproved real CLI `mcp__earshot__say` returned **"The user did not approve ... command was NOT run"**; no stored object containing the requested MCP probe text. The independently enabled final-reply hook did store the refusal summary; that is a separate side effect, not a successful MCP call. For this private, pre-authorized test only, `command_allowlist: ["mcp:earshot/say"]` granted that *one tool* in the throwaway profile, without weakening the server's trust tier. A new real CLI turn stored `msg_7eb82c389308446aba6bfbda10ad33d2`; matching phone beacons: detected 23:30:53.033Z, started 23:30:53.376Z, finished 23:30:58.137Z. Storing is not playback; `finished` means device playback completed, not that a person heard it.

A second bounded, explicitly invoked Hermes job (`scheduler: external`, `hermes cron run ... --wait --timeout 120`) called MCP `say` and stored `msg_cc01d5bfb5d64b3fad6f8574234e1c20`; its device receipt reached `finished` at 23:39:57.049Z. The no-tool job completed with `.extra.platform: cron`, with **zero** new object from the hook. Both jobs were removed afterward. No native recurring clock or Candybar registration was made.

## Path B: final-reply hook

See [`../examples/hermes/earshot-say.sh`](../examples/hermes/earshot-say.sh) (Linux: Bash, `jq`, `nohup`, `setsid`, installed relay CLI). The real hook payload has `.extra.assistant_response` and `.extra.platform`. The command loads `earshot.env` from the **active `$HERMES_HOME`**, not `$HOME`, because a multiplexed gateway scopes each profile; this run inherited the token but **not** the API URL, so inheritance alone was insufficient. Keep that file 0600 with `EARSHOT_API_URL` and `EARSHOT_API_TOKEN`; install the relay CLI and `jq` on the hook's PATH. Register the executable as `hooks.post_llm_call[].command`, using an absolute path; give the hook explicit consent (`hooks_auto_accept` or `hermes gateway run --accept-hooks`). It detaches with `setsid` so the reply is not blocked by a bucket write. Never put secrets or private replies in spoken output; the text is a plaintext private bucket object. The default allowlist includes the **observed** `cli`, `tui`, `ntfy` values and messaging names not verified here. Explicit `cron` and `subagent` are always excluded; Desktop is excluded until observed. Set `EARSHOT_HERMES_PLATFORMS` to narrow the allowlist. Running both path A and B can cause two spoken objects for one agent turn: enable only the path you intend.

A real CLI reply `EARS48 CLI corrected hook verification.` produced `.extra.platform: cli`, with the reply under `.extra.assistant_response`; relay object `msg_b662f66a1ff44c5b8837a0ea27d81f0a` has the matching `finished` receipt. A real multiplexed ntfy turn directly from `https://ntfy.delo.sh` produced `.extra.platform: ntfy`, `.extra.assistant_response: EARS48 ntfy hook verification.`, and relay object `msg_fea72474eb9b46c2b2aab8f44ee681c1` reached `finished`. A real Ink TUI turn produced `.extra.platform: tui`, `.extra.assistant_response: EARS48 TUI verified speak hook.`, and relay object `msg_2a2371cd1627453a9dbef3ad4e7aa5ef` reached `finished`. A test-only local ntfy proxy was briefly used to diagnose profile scoping before a new direct subscription to `ntfy.delo.sh` succeeded; the final ntfy row did not use the proxy. The multiplexed secondary profile's 0600 `.env` needed its *own* provider and ntfy credentials; an environment variable in the launch profile did not carry over. A publisher-controlled ntfy title is not an authorization identity: a private topic and authenticated subscription are required.
